# 数据库分布与访问关系

![数据库分布与访问关系](../../generated/diagrams/federated-twin-database-landscape.png)

图：联邦孪生平台数据库分布与访问关系图

系统按业务及部署边界分别管理数据库和文件存储。联邦学习平台、联邦学习支撑服务和各医院运行时代理分别使用 UmaDB 保存本服务业务事件，使用 PostgreSQL 保存查询视图及事件处理位置。服务消费事件并更新自身查询视图，不表示数据库之间直接同步或建立跨库外键。模型、上传文件和本地训练数据属于独立文件存储，不作为关系型数据库中的原始文件内容管理。

医院侧医疗数字人、风险动态评估与管理及其自身系统管理的数据归属于孪生应用。图中依据当前数据库设计说明的选型标注 PostgreSQL，并按患者、诊疗、监测、风险结果、用户权限和系统配置表示逻辑数据域；逻辑域不等同于多个独立物理实例，具体库和模式划分由孪生侧物理设计确定。孪生应用的数据库及文件资源不与联邦学习共用。

跨系统通过服务接口、业务标识和模型工件引用关联。平台向医院代理下发任务，代理回传元数据、模型更新及执行结果；原始训练样本保留在医院。联邦学习提供模型工件下载，下载后由应用推理侧部署，不以数据库直连、复制或共享表实现模型交付。云端推理侧的具体存储选型未在本图额外假设。

平台侧文件框表示该服务拥有或维护的本地工件，不表示平台与支撑服务共享同一文件卷。平台也可经支撑服务接口访问上传文件；应以具体工件的存储归属及引用解析规则确定访问方式。各医院代理重复采用相同逻辑结构，但独立维护自身事件、查询和文件数据。备份恢复应分别覆盖事件、查询库和文件工件，并核对处理位置及引用一致性。

## 放置位置

依据当前 V0.4 数据库设计说明的章节结构，本图放在第 3.6 节“数据库分布”，配合上述文字形成全系统总览。第 4 章各模块的“数据库概念设计”引用本图确定数据归属，再展开各自业务实体 ER 图。现有各模块章节顺序不变，不在某个模块内部放置全系统总览。

本图属于数据库架构与访问关系图，不是实体级 ER 图。实体级 ER 图应进一步描述组织、作业、轮次、计划、模型及患者、评估等业务实体和基数；未确认的跨系统实体关联不得直接画成外键。
