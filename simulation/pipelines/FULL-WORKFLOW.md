# Complete Remote Workflow

## Execution Ownership

Generic generated entries now handle task input/output and worker transfer:

```sh
node simulation/src/worker.mjs sync simulation/pipelines/worker.json
MEDOL_PIPELINE_RUN_ID=run-001 node simulation/src/task.mjs simulation/pipelines/tasks.json deploy
MEDOL_PIPELINE_RUN_ID=run-001 node simulation/src/task.mjs simulation/pipelines/tasks.json prepare-baseline
MEDOL_PIPELINE_RUN_ID=run-001 node simulation/src/task.mjs simulation/pipelines/tasks.json enroll-participants
MEDOL_PIPELINE_RUN_ID=run-001 node simulation/src/worker.mjs collect simulation/pipelines/worker.json
```

Run task commands on the selected worker (or locally for a local environment).
Tasks.json declares the selected project exports and input/output files; worker.json
declares sync inputs, excluded files and collected artifacts. Its hostRef reads
target and workDir from full-remote.json; changing that host updates both execution
and transfer destinations. Local execution omits transfer.
Task results are create-only and locked before execution; use a new run ID plus
manifest environment overrides when reusing inputs. Collection can be repeated and
never replaces differing evidence. Full-remote.json still runs the complete workflow;
use individual task commands when stopping after baseline or registration.

Business implementation remains in extensions/adapters/workflow-operations.mjs,
training-environment.mjs and training-stages.mjs. No business rules were moved into
the generator. See ../EXTENSIONS.md for the reusable extension contract.

Run from the repository root:

```sh
node simulation/src/run.mjs --mode remote --pipeline simulation/pipelines/full-remote.json --plan
node simulation/src/run.mjs --mode remote --pipeline simulation/pipelines/full-remote.json
```

To explicitly reuse published registry images without running build/publish:

```sh
node simulation/src/run.mjs --mode remote --pipeline simulation/pipelines/verify-published-images.json
```

This validates deployment and business execution only; it does not count as a
successful build/publish stage or bypass the generation-input integrity check.

This is an explicit opt-in replacement for the old combined remote-training flow.
The existing pipeline.json (existing deployment) and remote.json are unchanged.

## Stages

1. environment: sync worker inputs; create/reuse the configured K3d cluster.
2. build and publish: run Operations image tooling locally for linux/arm64.
3. deployment: generate private test configuration, verify registry images and
   deploy platform services plus participant slots (Agent, console and isolated
   databases). Agents are deployed before business registration. The project
   extension labels workers for the aggregation asset; this is not generic policy.
4. case-design: validate an explicitly reviewed approved-training.json.
5. data-preparation: independently initialize baseline authentication/dictionaries,
   then consume that baseline and approved cases to register the deployed slots
   with MANUAL_GUIDED, inject identity, bootstrap and await actual Agent connection
   reports; then prepare datasets and other business prerequisites.
6. test-execution: consume this run's data manifest and approved cases.
7. reporting: copy only deployment.json, data.json, test.json and failure.json
   from the worker. Missing evidence is marked unavailable, never passed.

The controller always writes simulation/reports/<runId>/report.json. Project
artifacts use simulation/reports/workflows/<runId>/ on both hosts. Failed normal
steps skip subsequent normal work but still run reporting. No rollback or cluster
deletion happens automatically. Evidence may contain business identifiers; protect it.

## Prerequisites and boundaries

- SSH alias fl-test and remote workDir are maintained in full-remote.json.
- Local build tooling, Docker, registry connectivity and registry credentials must
  be available. Maintain the Operations image configuration so push destinations
  match deployment.json-example's imagePrefix. No credentials are committed.
- Registry mirror configuration operations/k3s/cluster/registries.yaml is private
  worker configuration, excluded from sync. Provision it before a fresh-cluster run.
- Runtime Engine is an external project, not generated by the generic image build.
  Publish its required profile images separately; deployment verifies the aggregation
  image, and participant preparation needs the scenario's engine image as well.
- Dataset files must already be accessible through the configured worker mounts.
- Create and review simulation/cases/approved/training.json before running. The
  supplied training-acceptance.json remains a draft; this workflow never approves
  an AI/model/manual candidate automatically. Missing approval fails the run.
- This pipeline wires stages; it does not prove business test coverage or make
  arbitrary project commands idempotent. Plan mode does not execute live checks.

Use --stage build (or any stage name) for isolated execution. Declare verified
prerequisite step IDs in reuseCompletedSteps when selecting a dependent stage.
For data/test reuse, additionally provide an existingEnvironment manifest with
remoteManifestPaths.k3d. Testing existing data requires MEDOL_DATA_MANIFEST on the
worker; the fresh full pipeline uses its own run-specific data by default. A reuse
declaration alone does not copy manifests or imply they are still healthy.

## Seven-Step Runbook

There are seven workflow steps but eight CLI stage names: image build and publish
are independently selectable. Run local commands from the Federation Learning
repository root; run worker commands from `/home/fl-simulation/test` on `fl-test`.
Explicitly select `full-remote.json`: omitting `--pipeline` in remote mode still
selects the older `remote.json`, which is not this seven-step workflow.

| Step | CLI stage | Execution host | Completion criterion |
| --- | --- | --- | --- |
| 1. Environment preparation | environment | Local sync, remote K3d | API reachable, nodes ready, explicit kubeconfig available |
| 2. Image build and publish | build + publish | Local Docker, target registry | Required target-architecture images published and resolvable |
| 3. Service deployment | deployment | Remote K3d | Selected services and participant slots ready; deployment.json written |
| 4. Case design and review | case-design | Author locally, check remotely | Explicitly reviewed approved-training.json passes validation |
| 5. Business data preparation | data-preparation | Remote, via business APIs | Registration, connection and dataset readiness pass; data.json written |
| 6. Test execution | test-execution | Remote | Approved actions and assertions pass; test.json written |
| 7. Result collection | reporting | Local controller | Whitelisted remote evidence copied and missing evidence identified |

### 1. Prepare The Environment

Maintain these inputs before running:

- `full-remote.json`: SSH target `fl-test` and remote work directory.
- `environment-isolated.json`: environment, cluster configuration, worker count and kubeconfig output.
- `extensions/fixtures/k3d-isolated.yaml`: K3s image, API port and host port mappings.
- Remote `operations/k3s/cluster/registries.yaml`: registry mirror/access configuration.

Environment preparation creates or connects infrastructure only. It does not
register organizations, allocate runtime identities or submit training jobs.
The current configuration has one server and two workers. Worker count and Agent
count are separate settings. The current project data helper assigns one worker
per participant; preparing 20 participants therefore requires 20 workers until
that business scheduling policy is changed.

Always use the Simulation kubeconfig, not the machine's default Kubernetes context:

```sh
export KUBECONFIG=/home/fl-simulation/test/operations/k3s/.work/kubeconfig-federation-learning-local.yaml
kubectl get nodes -o wide
kubectl get deployments -A
```

The same host also has a separate native K3s installation. Do not operate on it
through an implicit context. The Simulation platform uses host port 31080, not 30080.

### 2. Build And Publish Images

The remote worker is ARM64, regardless of the local development machine's CPU:

```sh
node operations/images/images.mjs build --environment local --platform linux/arm64
node operations/images/images.mjs push --environment local --platform linux/arm64
```

Ensure the image configuration's push prefix matches `deployment.json-example`:
currently `192.168.50.2:5000/fl`. External Runtime Engine profile images and base
dependency images must also exist in the reachable registry. The full pipeline's
build/publish commands do not automatically build Runtime Engine or publish all
offline dependency images. CSV training currently selects the `sklearn` profile;
the platform aggregation asset currently uses `pytorch-vision`. Check both.

Existing verified images can be reused; an architecture mismatch must not be
solved by repeatedly rebuilding an image for the wrong target. Keep published
references/digests and build evidence. Image availability is not training validation.

### 3. Deploy Before Registration

`deployment.json-example` controls platform `instances`, `participantSlots` and
`participantAccess`. Currently two participant slots are deployed. Each has a
separate namespace, Agent, console, gateway, PostgreSQL and UmaDB storage:

| Site | Namespace | Browser URL |
| --- | --- | --- |
| Platform | federation-learning-platform | http://192.168.50.2:31080 |
| Participant 1 | federation-learning-platform-p1 | http://192.168.50.2:31081 |
| Participant 2 | federation-learning-platform-p2 | http://192.168.50.2:31082 |

The Agent may be healthy while waiting for identity configuration. This means
deployment-ready, not business-ready. Do not deploy orphan participant consoles.
No platform-managed Agent deployment command is required in this workflow.

K3d reserves host ports 31081-31100 for NodePorts 30081-30100. Each participant
gateway serves its own console and Agent; authentication/support routes reach
shared Support. The Agent's reported endpoint is cluster DNS, not its browser URL.
See [Participant Deployment](../extensions/PARTICIPANT-DEPLOYMENT.md).

For an existing cluster, application apply does not add Docker port mappings.
Check existing mappings first. The following command was used to add the range
without deleting data; do not add it again if already present:

```sh
k3d cluster edit federation-learning-local --port-add '31081-31100:30081-30100@server:0'
```

This recreates the K3d load-balancer container and briefly interrupts access.
Do not delete the cluster merely to update an application image or ConfigMap.

### 4. Design And Approve Cases

Cases can originate from model specs, AI suggestions or manual authoring. Model
output is a candidate, not proof of a correct complete business journey. Review
prerequisites, command payloads, assertions and supported executor actions.

```sh
node simulation/src/cases.mjs validate simulation/extensions/scenarios/training-acceptance.json
# Only after reviewing and resolving draft issues:
node simulation/src/cases.mjs approve simulation/cases/manual/training.json simulation/cases/approved/training-v2.json reviewer-name
node simulation/src/cases.mjs check simulation/cases/approved/training-workflow-v2.json
```

Training uses the generic HTTP executor. Commands, queries, loops and artifact assertions are defined in approved cases. The pipeline selects reviewed cases; it does not author or approve them automatically. Case design can happen before deployment.

### 5. Register And Prepare Business Data

This stage consumes a ready deployment report with participantDeployments. It:

1. Initializes shared authentication and dictionaries.
2. Creates/reuses organizations, federation membership, feature schema, initial
   model, runtime infrastructure records and training run configuration.
3. Registers each already-deployed Agent with MANUAL_GUIDED.
4. Applies project-specific worker labels/taints, injects identity through the
   participant-enrollment ConfigMap, then restarts the existing Agent.
5. Calls LoadRuntimeAgentBootstrapConfiguration and waits for the Agent's real
   connection report and runtime identity. The script does not fabricate reports.
6. Declares/binds datasets and checks business readiness before writing data.json.

The current `two-participant-training.json` selects CSV. On the worker, the default
input is `/home/fl-simulation/test/volumes/datasets/test.csv`; Agent and Engine see
`/workspace/datasets/test.csv`. These are different filesystem locations.
The source file must exist and match the seeded feature/label schema. It must also
be mounted or copied into the K3d worker nodes and exposed to the pods. Creating a
host directory alone does not populate the K3d node filesystem. A Kubernetes
hostPath here refers to the node container, not directly to the SSH host.

The sync script excludes data volumes. The scenario's `fixtures` configuration
declares the source file, SHA-256, local copy and destination paths. The generated
fixture transport queries the explicit kubeconfig,
validates that destinations are this K3d cluster's worker containers, and copies
the fixture into each node's `/workspace/datasets/test.csv` before registration.
Other datasets require their own provisioning; this is not a generic Kubernetes
data-copy mechanism. Raw training data is not generated by the model exporter.

Baseline data preparation depends on deployment, not on case approval. Case-specific
fixtures additionally depend on their selected reviewed cases. Registration-only
evidence is not a ready-data manifest and must not be passed to test execution.

### 6. Execute Tests

Execution consumes both data.json and approved-training.json. It rechecks fixture
identity/readiness, submits training and verifies the result. It must not recreate
the environment or register replacement Agents to hide stale/missing data.
An accepted HTTP command, a healthy pod, or a COMPLETED local round alone is not
proof that the complete federated training assertions passed.

### 7. Collect Results

The pipeline summary is `simulation/reports/<runId>/report.json` locally. Project
evidence is `simulation/reports/workflows/<runId>/` on each host. The collector
currently whitelists deployment.json, data.json, test.json and failure.json;
it writes evidence.json describing copied/missing files. It does not collect
secrets, arbitrary logs or the manually produced enrollment.json automatically.

Failed normal steps skip later normal work; reporting still runs. Missing evidence
is unavailable, never passed. Keep failure evidence when resuming. No automatic
rollback deletes already accepted business commands or provisioned resources.

## Credentials, CORS And Retry Safety

- `prepare-test-environment.mjs --auto-test` generates/reuses private test secrets.
  `.env`, `simulation/test-environment.private.json` and `secrets.local.yaml` remain
  on the worker and must not be committed or pasted into reports. Existing divergent
  credentials cause refusal, not silent replacement. This is not production secret management.
- Deployment does not create the admin account. Data preparation initializes
  `simulation-admin` with the managed private password; do not assume admin/admin.
  Service calls use the shared internal token, not a browser login token.
- Add actual browser origins, including each participant's host port, to operations
  `config/local.yml` browserOrigins. Current entries cover 31080, 31081 and 31082.
  Adding further participants requires corresponding origins. Apply regenerated
  ConfigMaps and restart applications that read environment variables at startup.
- Do not replace endpoint fields with localhost when called from another container.
  Check browser URLs, gateway routes and cluster service URLs separately.
- Reuse the same participant keys and training-run key when retrying preparation.
  A slot already enrolled to another infrastructure is rejected deliberately.
- Project evidence files are create-only. Use a new run ID for a new attempt and
  reference the verified prior deployment/data manifest instead of deleting evidence.
  `--stage` does not run dependencies automatically. `reuseCompletedSteps` lists
  step IDs, not stage names, and is an operator declaration requiring verification.

To prepare or test against an existing deployment on the worker, use a new run ID:

```sh
export MEDOL_PIPELINE_RUN_ID=retry-training-001
export MEDOL_ENVIRONMENT_MANIFEST=/absolute/path/to/deployment.json
node simulation/src/task.mjs simulation/pipelines/tasks.json prepare-baseline
export MEDOL_BASELINE_DATA_MANIFEST=/absolute/path/to/baseline.json
node simulation/src/task.mjs simulation/pipelines/tasks.json prepare-case
# Only after data preparation succeeds and reviewed cases are available:
export MEDOL_DATA_MANIFEST=/absolute/path/to/data.json
node simulation/src/task.mjs simulation/pipelines/tasks.json test
```

Do not use the environment-preparation manifest in place of deployment.json.
Older reports that omit imagePrefix need an explicit FL_APP_IMAGE_PREFIX override
or a new deployment report. Verify the selected manifest points to the intended
cluster before executing business commands.
